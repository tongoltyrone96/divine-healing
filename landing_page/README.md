# strawberryhope.com — landing page

The page the client's ads point to. It is a single static page with no
build step: `site/` is exactly what gets deployed.

```
site/
  index.html        all nine sections of the brief
  css/styles.css    the app's palette and type (lib/theme.dart)
  js/main.js        store routing for the Download buttons
  fonts/            Playfair Display and Nunito, latin subset, self-hosted
  img/              generated by tools/make_assets.js, except badge-app-store.svg
  vercel.json       cache headers
tools/
  make_assets.js    builds site/img from the app's own artwork
  src/              sources that do not live in the app (the Google Play badge)
```

## The brief, and where the page departs from it

The brief came from the client on 2026-10-05 as WhatsApp screenshots of a
Copilot chat (kept locally in this folder, not committed). The section order
and wording follow it, except where the app does not do what the brief says.
An ad can only promise what a subscriber actually gets.

| Brief | Page | Why |
|---|---|---|
| Premium $150/year | CAD $149/year | The real price, matching both stores and Stripe |
| Premium includes monthly live meditation, priority booking, intuition development, Reiki sessions | Left out | Not in the app. Free users can book too, and Reiki in the app is an introduction plus booking |
| "Start with a free grounding meditation" | "Start with a free meditation" | Grounding is a paid session. The free ones are Anxiety Release (10 and 5 min) |
| Testimonials, 3–5 placeholders | Section held back | Made-up reviews break consumer law and ad-platform policy. Add real ones with permission |
| Practitioner photo | The emblem, in a round frame | No photo was supplied, and using someone else's photo as hers would mislead. Swap in `about__photo` |
| Built in Wix or Squarespace | Static site on Vercel | Faster for ad traffic, no monthly fee, matches the app exactly |

A footer line says the app is not a substitute for medical or mental-health
care. The brief does not ask for it; ads about anxiety and healing need it.

Screenshot 03 (the Reiki page) is not used: it says balanced energy makes
you "less likely to get sick", which is a health claim.

## Meta Pixel

The client's own pixel, ID `1099251262520848`, created in her Meta
Events Manager and emailed on 2026-10-07. The base code is in the
`<head>` of `index.html`, and the click events are in `js/main.js`:

| Event | When |
|---|---|
| `PageView` | every visit (base code) |
| `DownloadApp` (custom) | a tap through to either store, with `store: app_store / google_play` and the `section` it was in |
| `Lead` (standard) | a tap through to the Calendly booking page, with the `section` |

Neither event is a completed install or booking, because those happen in the
stores and on Calendly. Store badges open in a new tab so the event is
sent before the page goes away.

Verified on the live domain by driving Chrome over DevTools and watching
the requests to `facebook.com/tr`. **Headless Chrome sends nothing**, so
it needs a normal user agent and `--disable-blink-features=AutomationControlled`.
Otherwise the pixel loads and silently drops every event.

Meta's terms require a site that uses the pixel to say so, which is what
`/privacy` and the footer's "Privacy" link are for. There is no cookie
banner, which is fine for ads in Canada, the US and Australia. One is needed
before advertising in the EU or UK.

## Download buttons

The client's brief of 2026-10-12 put downloads first: **every download
control goes straight to a store, and nothing scrolls**.

- **Hero and final section**: the two official store badges are the main
  action, the largest tappable thing in the hero. Booking is out of the
  hero, and in the final section it sits below the badges.
- **Other "Download" buttons** (free meditation, both pricing cards) carry
  `data-app-link`. An inline script in `<head>` puts `os-ios`, `os-android`
  or `os-other` on `<html>` before the first paint, and `js/main.js` points
  the buttons at that phone's own store. A computer has no store of its own,
  so under `.os-other` CSS hides the button and shows the
  `.badges--desktop` pair beside it instead.
- On a computer, store links open in a new tab, so the pixel event is sent
  before the page goes away. On a phone the store app takes over and the
  page stays, so they stay in the same tab.
- Without JavaScript the buttons fall back to `#get-the-app`, where the
  final section's badges are.

Check with a real phone viewport, not a narrow desktop window: the routing
depends on the user agent.

## Changing images

```
cd landing_page
npm install --no-save sharp
node tools/make_assets.js
```

Replace a source (a screenshot in `store/ios/`, the icon in
`divine_healing/assets/logo/`) and re-run. Nothing in `site/img` is edited by
hand.

## Previewing locally

Any static server on `site/`. Headless Chrome cannot be trusted below about
500px wide, because the desktop window has a minimum width and narrower
screenshots are crops of a wider page. Put the page in a 390px iframe to
see a real phone width.

Desktop Chrome is not the bar. On the client's family Huawei MGA-LX3
(Android 10, Chrome 149) the "What the app helps with" cards rendered as a
smeared stack of copies of themselves, while desktop was flawless.

**The cause was translucent borders on rounded boxes**, `border: 1px solid
rgba(...)` together with `border-radius`. That was found by bisecting on the
device over Chrome DevTools: reload, jump to the same scroll position,
screenshot, with one CSS override at a time. The original page corrupted
every time. Opaque borders, no borders, or square corners were each clean
every time. Shadows, gradients, fonts, the sticky header, images and the
rotated phone made no difference.

So: **every border colour is opaque** (`--border: #EAD6DA` is rose gold at
35% over white). Never put an `rgba()` colour in a border. The phone
frame's rim is an inset box-shadow in the same opaque colour.

Earlier guesses removed the frosted header, the scroll-reveal animation and
the translucent card fills before the real cause was known. Those changes
stayed because they cost nothing, but they were not the fix.

To test on a device: `adb reverse tcp:4173 tcp:4173` to serve the local
page, `adb forward tcp:9222 localabstract:chrome_devtools_remote` to drive
Chrome. A tab in the background does not run `requestAnimationFrame`, so
activate it (`/json/activate/<id>`) before scripting it.

## Caching

`css/` and `js/` are cached for an hour, so `index.html` loads them as
`styles.css?v=N` and `main.js?v=N`. **Bump N with every change to either
file**, or phones that visited in the last hour keep the old one. HTML is
not cached, so the new number reaches them at once.

## Deploying

Vercel project **strawberryhope** in the `tyrone-jher-tongols-projects`
scope, deployed from `site/` with the CLI (no Git integration):

```
cd landing_page/site
npx vercel deploy --prod --yes --scope tyrone-jher-tongols-projects
```

Live at https://strawberryhope.vercel.app until the domain is pointed here.

`vercel link` writes a `.env.local` holding a `VERCEL_OIDC_TOKEN` into this
folder. A static site needs none of it, so delete it. `.vercelignore` keeps
`.env*` out of every upload regardless, which is checked by
`/.env.local` answering 404 on the live site.

That scope is on the **Hobby** plan, which Vercel's terms limit to
non-commercial use. It is fine for the client to review the page. Running
paid ads to it needs Vercel Pro or another host. Cloudflare Pages is free
and allows commercial use, and since the site is plain files, it moves
without changes.

`ns55/ns56.domaincontrol.com`) and currently serves a near-empty GoDaddy

Vercel project on 2026-10-07. At GoDaddy → DNS, these are the records
Vercel asked for (`vercel domains verify <domain>`), replacing the Website
Builder ones (A `76.223.105.230` and `13.248.243.5`, CNAME www → @):

| Type | Name | Value |
|---|---|---|
| A | @ | 216.198.79.1 |
| A | @ | 64.29.17.1 |
| CNAME | www | 4589ee7747605a2f.vercel-dns-017.com |
