## Move order (after `flutter create` finishes)

1. Replace `pubspec.yaml` with the prepared one
2. `flutter pub get`
3. Place `lib/theme.dart` (from the scaffold)
4. Place `assets/content/*.json` (from data/content/)
5. `flutter pub run build_runner build` (Freezed / Riverpod codegen)
6. Place `main.dart` + `router.dart`
7. Scaffold the `features/` folders

## Route map (Glide URLs preserved)

| Flutter route | Glide URL | Screen |
|---|---|---|
| `/` | `/` | Home |
| `/library` | `/library` | Library (all) |
| `/library/:category` | `/library/meditation` etc. | Library filtered |
| `/content/:id` | `/content/15` | Session detail + player |
| `/profile` | `/profile` | Profile |
| `/chakras` | `/chakras` | Chakra Healing |
| `/affirmations` | `/affirmations` | Affirmations |
| `/breathing` | `/breathing` | Breathing techniques |
| `/manifestation` | `/manifestation` | Manifestation journey |
| `/spiritual-awakening` | `/spiritual-awakening` | Spiritual Awakening |
| `/booking` | `/booking` | Booking (Zoom / Square) |
| `/shadow-work/:id` | (Glide uses a separate route) | Shadow work journey (explain → listen → reflect) |
| `/sign-in` | (Glide handles this on Home) | Sign-in screen |

## Why this structure?

- **Feature-first**: each screen owns its widgets and logic, minimising conflicts when the team grows.
- **Repository pattern**: local JSON for M1, Supabase for M2 — swap without touching widget code.
- **Static vs dynamic split**: chakras / affirmations etc. ship as local assets; only session content comes from Supabase.
- **Riverpod providers**: state management is explicit and easy to test.
